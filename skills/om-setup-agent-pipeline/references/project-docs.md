# Project docs: SDLC.md, AGENTS.md, CODE_REVIEW.md, BACKWARD_COMPATIBILITY.md

Beyond the config, this skill produces the human-readable half of the pipeline. Every document below is **derived from the current project, never copied from someone else's**: generate content from what this repository actually contains (stack, layout, public surfaces, conventions detected in the code). Each is generated only when missing — an existing file is never touched, and the skills take existing files into consideration exactly as they would generated ones.

## Existing-project reconciliation (read this before generating anything)

A repo with 90+ modules and a decade of conventions is not the same starting point as an empty one, and the skill must not treat it as one. Before generating *any* of the four docs below, check for an existing agent instruction file (`AGENTS.md`, `CLAUDE.md`, or equivalent) and existing process docs (`CONTRIBUTING.md`, an internal wiki export, a `SDLC.md`/`CODE_REVIEW.md` already at root under a different name). This is not only about whether `AGENTS.md` itself gets overwritten — it never is (see below) — it is about whether the *other three* docs, which the skill still generates by independently scanning the repo, end up contradicting rules the existing file already establishes (a different validation gate, a different module-boundary convention, a different definition of what counts as a breaking change). Generating those in isolation is how a first-run on an established repo silently redirects the pipeline the team actually follows.

Concretely, when an existing agent instruction file (or equivalent) is present:

1. **Read it in full first**, before scanning the repo for stack/conventions. Extract anything it already states that overlaps a doc this skill is about to generate: validation/test commands, module or layer boundaries, contract-surface rules (APIs, schema, CLI, config), review priorities, naming conventions.
2. **Ask the reconciliation mode per doc** (see the new interview question in `references/interview-questions.md`) rather than defaulting to either "skip" or "generate independently":
   - **Link** — generate a short doc that points at the existing file's relevant section instead of restating it (lowest risk, use when the existing file already covers the ground well).
   - **Merge** — generate the doc from the template as usual, but seed each section with the existing file's stated conventions where they overlap, flagging in the draft (before showing it to the user) anywhere the repo-scan disagreed with what the existing file says.
   - **Offer-diff** — show the user, side by side, what would be generated from scratch vs. what the existing file already implies, and let them pick per-section.
   - **Skip** — still available, and still the right call when the existing file plus other docs already fully cover that concern.
3. **Never silently pick a default.** If the user is unavailable (`--defaults` run), the safe default is **link, not generate independently** — a short doc pointing at the existing conventions is far less likely to redirect the pipeline than a freshly-scanned one, and the run must say explicitly in its report that this happened and why, so a human can revisit it.
4. This applies per document — a repo can have a rich `AGENTS.md` but no `BACKWARD_COMPATIBILITY.md` equivalent at all, in which case that one doc generates normally from a repo inventory (nothing to reconcile against).

- `SDLC.md` (repo root) — the team's ticket flow: pipeline stages, the label state machine, the QA gate, the claim protocol, and which skill drives each stage. Generate it from `references/sdlc-template.md`, filling in the resolved base branch, tracker, specs directory, label mode, QA gate, and validation commands; the product-layer blocks (`IF discovery`) render only when the config already carries `discovery.enabled`, and then between the `discovery:start` / `discovery:end` markers `om-setup-discovery-pipeline` owns. When the repo already documents its process (in a dedicated doc, or embedded in `AGENTS.md`/`CLAUDE.md`), apply the reconciliation mode chosen above instead of overwriting it.
- `AGENTS.md` — agent instruction files (`AGENTS.md`, `CLAUDE.md`, or equivalents) are where a project records its own specifics; every skill in this collection reads them before working. When the repo has no such file, offer to generate one. **When one already exists, it is never overwritten or regenerated — full stop; that part of the behavior is intentional and already correct.** What still needs deciding in that case is whether the *other three* docs below should be generated independently or reconciled against it — see Existing-project reconciliation above. The generated file (fresh-setup case only) contains, all derived from *this* repository:
  - A one-paragraph project overview (from the README, or ask).
  - A **task-routing table** — the core of the file: rows mapping task types to the files an agent must read and the rules that apply, built by scanning the repo structure. Shape: `| When the task involves… | Read first | Key rules |` with one row per significant area (e.g. each top-level package/app/module group, the API layer, the UI layer, tests, CI). Populate `Read first` with real paths discovered in the repo and `Key rules` with conventions detected in the code (naming patterns, error handling, how existing code does data access); leave `TODO` markers where nothing can be inferred rather than inventing rules.
  - The validation commands from the config, and pointers to `SDLC.md`, `CODE_REVIEW.md`, `BACKWARD_COMPATIBILITY.md`, and `.ai/agentic.config.json`.
- `CODE_REVIEW.md` (repo root) — the repo's code-review rules as a standalone human-editable document, complementing (not replacing) the `reviewChecklist` config field. Generate it from the project itself: the detected stack's high-signal review points, the conventions observed in the codebase, the validation gate, and the label/severity discipline the pipeline uses. Structure: review priorities (correctness, security, contracts), repo-specific checks (derived — e.g. "all HTTP handlers validate input with <the validation library actually used here>"), and severity guidance. When an existing `AGENTS.md`/`CLAUDE.md` already states review priorities or a minimal-diff/override policy (common in a codebase that wraps a vendor framework), reconcile per the mode chosen above instead of independently re-deriving something that may conflict. `om-code-review` (and therefore `om-auto-review-pr`) automatically applies this file when present.
- `BACKWARD_COMPATIBILITY.md` (repo root) — what this project considers a **protected contract surface** and how changes to one must be handled. Generate it by inventorying the repo's actual public surfaces: exported package APIs, HTTP routes and response shapes, CLI commands and flags, DB schema/migrations, config file formats, published events/webhooks — whichever of these the repo actually has. For each surface: what counts as a breaking change, and the required path (deprecation window, migration note, version bump). When an existing `AGENTS.md`/`CLAUDE.md` already enumerates protected surfaces or an "ask first" list for contract-affecting changes, reconcile per the mode chosen above — an independently-scanned inventory can easily miss (or contradict) surfaces the team already flagged as sensitive for reasons not visible from the code alone (e.g. an external integration with no in-repo trace). Review skills check changes against this file; implementation skills warn the user whenever a change violates it.
